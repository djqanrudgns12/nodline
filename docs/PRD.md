# 노드라인 (Nodeline) — 마스터 PRD 및 개발 에이전트 통합 명세서 (v3.1)

> **앱 이름 / 버전**: **노드라인 (Nodeline)** `v1.0.0`  
> **앱 아이콘**: 2-B 실제 인게임 도면+열차 시안 (`icon.ico`, `icon.svg`, `icon.png`, `assets/icons/`, `web/icons/`, `web/favicon.ico`, `web/favicon.svg`, `web/manifest.webmanifest`)  
> **문서 목적**: 초보 바이브코더가 개발 에이전트/아키텍트에게 그대로 전달하여 추측 없이 즉시 구현하고 검증할 수 있는 최종 통합 마스터 명세서  
> **대상 플랫폼**: Windows x64 (단일 EXE) & Web HTML5 Canvas (Localhost 웹 브라우저 플레이 지원)  
> **최종 배포 목표**: Windows 단일 실행 파일 (`SubwayGame.exe`) 및 웹 로컬호스트 서비스 (`http://localhost:3000`)  
> **기본 기술 스택**: Godot 4.3 Standard + GDScript / HTML5 Canvas + Vanilla JS  
> **디자인 테마**: **디자인 2: 노르딕 아키텍처 라이트 (Nordic Architectural Light / Clean Paper Blueprint)**  
> **핵심 설계 원칙**: TCREI + CRUD + 클린 아키텍처 + CQRS + 데이터 중심 설계 + 테스트 가능한 핵심 로직

# 0. 개발 에이전트 페르소나 및 행동 강령

너는 **수석 게임 아키텍트 + 수석 Godot 개발자 + UI/UX 시스템 설계자**다.  
사용자는 초보 바이브코더다. 따라서 “코드를 빨리 작성하는 것”보다 다음 6가지 원칙을 최우선으로 둔다.

1. 요구사항이 정확하게 구현되는가?
2. 나중에 수정하기 쉬운가?
3. 오류가 발생했을 때 복구할 수 있는가?
4. 게임 핵심 규칙을 자동으로 테스트할 수 있는가?
5. UI가 실제 기능을 편하게 사용할 수 있도록 만들어졌는가?
6. 사용자가 이해하지 못할 결정을 개발자가 몰래 대신하지 않았는가?

## 0.1 최우선 품질 순서
겉보기만 좋은 게임을 만들지 않으며, 반드시 아래 우선순위를 따른다.

**규칙 정확성 > 유지보수성 > 테스트 가능성 > 사용 편의성 > 시각적 완성도 > 미세한 성능 최적화**

게임 규칙이 정확하게 동작하고, 잘못된 행동에서 복구되고, 나중에 확장하기 쉬운 구조를 먼저 만든다.

## 0.2 작업을 시작할 때의 행동 절차
1. 현재 프로젝트 디렉터리와 이미 존재하는 파일/코드를 조사한다.
2. 본 PRD 요구사항을 가장 작은 구현 단위 항목으로 나눈다.
3. 본 문서의 4장(확정된 ADR) 설정값을 기본값(Baseline)으로 적용하되, 변경이 필요한 정책이 생기면 사용자에게 A/B/C 선택지를 제시한다.
4. 결정된 내용은 ADR(`docs/adr/decisions.md`)에 기록한다.
5. 게임 핵심 도메인 로직부터 가장 작은 단위로 구현하고, 각 단계마다 자동 테스트를 실행해 검증한다.
6. 핵심 로직이 완성되기 전에 화려한 UI부터 만드는 식으로 진행하지 않는다.

## 0.3 개발 에이전트 절대 금지사항
- 이미 사용자가 말한 내용을 다시 묻지 않는다.
- 사용자가 요청하지 않은 별도 서버(외부 Node, Python 등), 외부 DB, 클라우드 저장, 로그인/계정 API를 절대 추가하지 않는다.
- 불필요하게 최신 베타/개발판 엔진이나 검증되지 않은 외부 라이브러리를 추가하지 않으며, 테스트 문제를 엔진 버전 업으로 억지로 해결하지 않는다.
- `Main.gd` 하나에 모든 게임 로직을 넣거나, `Station.gd` 하나가 승객 생성·저장·경로 계산·UI를 전부 담당하게 만들지 않는다.
- 모든 것을 전역 Singleton(Autoload)이나 전역 상태로 만들지 않는다.
- 코드 곳곳에 매직 넘버(Magic Number)를 직접 적지 않는다.
- 오류를 조용히 무시하거나 숨기지 않는다.
- 라이선스 확인 없이 외부 코드/에셋을 사용하거나 다른 상용 게임의 UI/아트/그래픽/코드를 복제하지 않는다.

## 0.4 외부 참고 자료 활용 우선순위
1. 1순위: 공식 Godot 문서
2. 2순위: 공식 Godot 데모 프로젝트
3. 3순위: 라이선스를 명확히 확인한 공개 GitHub 코드
4. 4순위: Reddit 등 커뮤니티 경험 사례 (게임 설계 아이디어, 불편 사항, UX 참고용으로만 쓰며 공식 규칙이나 정답으로 삼지 않는다)

# 1. 제품 개요 및 목표

## 1.1 프로젝트 한 줄 설명
플레이어가 산과 강이 존재하는 지형 위에 지하철 노선을 연결하고, 열차를 운행하여 승객을 목적지까지 이동시키는 **2D 지하철 건설/운영 시뮬레이션 게임**이다. 어느 한 역의 대기 승객이 **15명에 도달하는 순간 게임이 종료**된다.

- **핵심 게임 루프**: `노선 연결 → 열차 운행 → 승객 증가 → 병목 발생 → 지도 확장 & 신규 역 등장 → 노선 재설계 → 혼잡 해소 → 더 많은 승객 처리`
- “예쁜 도시를 보는 게임”이 아니라 **노선 설계와 혼잡 해결 자체가 재미의 핵심인 게임**으로 설계한다.

## 1.2 제품 10대 목표
1. 처음 실행한 사용자가 5초 안에 화면의 구조를 파악할 수 있어야 한다.
2. 약 30초 이내에 첫 지하철 노선을 만들 수 있어야 한다.
3. 게임을 일시정지한 상태에서 안전하게 노선을 수정할 수 있어야 한다.
4. 강과 산이 단순한 배경이 아니라 노선 설계를 방해하는 실제 게임 요소여야 한다.
5. 역당 최대 5개 연결 제한으로 자연스럽게 병목이 발생해야 한다.
6. 객차당 5명이라는 용량 제한이 노선 설계의 중요한 변수여야 한다.
7. 특정 역의 승객이 15명에 도달하면 명확하게 게임이 종료되어야 한다.
8. 핵심 게임 규칙은 UI 없이도 테스트할 수 있어야 한다.
9. 인터넷이 연결되지 않아도 전체 게임이 정상적으로 실행되어야 한다.
10. 최종적으로 Windows에서 가능한 한 **파일 하나(단일 EXE)** 및 웹 브라우저(Localhost)에서 완벽히 실행되도록 한다.

## 1.3 만들지 않을 것 — 초기 버전(MVP) 제외 범위
다음 기능은 MVP에서 절대 구현하지 않는다:
- 온라인 멀티플레이, 계정/로그인, 서버, 실시간 통신, 온라인 랭킹, 광고, 결제, 3D 도시, 클라우드 저장, 챗봇, 생성형 AI 기능, 복잡한 경제 시스템.

# 3. 핵심 설계 원칙: TCREI & CRUD

## 3.1 TCREI 원칙
- **T — 추적 가능성 (Traceability)**: 모든 요구사항은 `요구사항 ID → 응용 기능 → 도메인 규칙 → 자동 테스트 → 도메인 이벤트`로 1:1 연결되어야 한다.
- **C — 일관성 (Consistency)**: 같은 의미는 프로젝트 전체에서 항상 같은 데이터와 같은 UI 패턴으로 표현한다.
- **R — 복원력 (Resilience)**: 잘못된 조작이나 저장 오류가 발생해도 게임 전체가 죽지 않고 이전 상태로 복구할 수 있어야 한다.
- **E — 확장성 (Extensibility)**: 추후 역 종류, 색상, 승객 규칙, 시간대, 지형, 열차, 게임모드, 난이도, 이벤트 등을 코드 대규모 수정 없이 데이터와 정책 추가로 확장할 수 있어야 한다.
- **I — 구현 가능성 (Implementability)**: 개발자가 추측해서 구현하지 않도록 모든 인터페이스 계약과 수치 규칙을 명확하게 정의한다.

# 4. 확정된 아키텍처 결정 기록 (ADR D-01 ~ D-16)

모든 수치는 코드에 하드코딩하지 않고 `res://data/balance/default_balance.tres` 설정 리소스로 분리한다.

| ID | 결정 항목 | 확정 선택 | 상세 구현 명세 |
|---|---|---|---|
| D-01 | TCREI 정의 | A (표준 정의) | 3.1절에 정의된 Traceability, Consistency, Resilience, Extensibility, Implementability 강제 |
| D-02 | 승객 목적지 결정 | B (모양 후보 + 색상 우선) | 1) 승객 모양과 같은 역 후보군 추출 → 2) 그중 승객 색상과 같은 역 우선 선택 → 3) 최단거리/최소비용 역 최종 선택 |
| D-03 | 시작 열차 구성 | A (열차 1대 + 객차 1개) | 시작 시 열차 1대(객차 1개 포함, 용량 5명) 지급 |
| D-04 | 노선 형태 | B (웨이포인트 연결) | 역과 역 사이에 중간 지점(Waypoint)을 넣어 산/강을 우회할 수 있는 폴리라인 방식 |
| D-05 | 다리/터널 자원 | B (제한된 자원) | 초기 지급량(다리 1개, 터널 1개)으로 시작, 플레이 중 보급, 노선 철거 시 100% 인벤토리 반환 |
| D-06 | 노선 교차 규칙 | B (교차 허용 + 열차 속도 감소) | 역이 아닌 선로 교차 구간 통과 시 속도 40% 감속(0.6배속) |
| D-07 | 시뮬레이션 배속 | B (일시정지 / 1x / 2x / 4x) | `0x`, `1x`, `2x`, `4x` 지원 |
| D-08 | 점수 시스템 | C (네트워크 효율 + 생존 시간) | `총점 = (도착 승객 × 10) + (생존 일수 × 50) + 네트워크 효율 보너스` |
| D-09 | 저장 방식 | B (수동 저장 + 자동 저장) | 수동 저장 3슬롯 + 주요 이벤트/주기적 `autosave.json` |
| D-10 | 초기 역 무결성 규칙 | 100% 무중복 & 무장애 보장 | 형태 3종(원/삼각/사각) + 색상 3종(코발트/코랄/에메랄드) 1:1 고유 배정 + 3개 역 상호 간 직선 경로 무장애 보장 |
| D-11 | UI/시각 디자인 시스템 | 디자인 2: 노르딕 아키텍처 라이트 | 웜 아이보리 페이퍼(`#F8F6F0`) + 64px 아키텍처 그리드 + 스칸디나비안 블루 강(`#A2C5DC`) + 세이지 그레이 산(`#DCE3DB`) + 순백색 플로팅 카드 UI |

# 5. 클린 아키텍처 및 프로젝트 구조

## 5.1 아키텍처 데이터 흐름 및 CQRS
핵심 게임 규칙(Domain)은 UI(Presentation)와 완전히 분리한다. UI가 역이나 열차 객체 내부의 값을 직접 수정하는 것을 엄격히 금지한다.
- **기본 흐름**: `UI → 응용 기능(Application) → 게임 규칙(Domain) → 이벤트 발생(Domain Event) → 화면 표시 업데이트(Presentation)`
- **명령(Command)**: 노선 생성/연장/순환, 노선 수정, 노선 삭제, 다리 건설, 터널 건설, 일시정지, 배속 변경, 새 게임 시작
- **조회(Query)**: 역 상태 조회, 노선 상태 조회, 네트워크 KPI 조회, 최근 이벤트 조회, 게임 결과 조회

## 6.2 역 (Station) 및 맵 생성 시스템 상세 사양
### 6.2.0 강 지형 굴곡 및 형상 사양 (D-27)
- 세로 중앙선(`centerY`)을 y축 0 기준선으로 설정.
- 가로 정중앙은 0에 수렴하고, 좌우 구간은 다중 주파수 코사인 보간 곡선을 통해 -75px ~ +75px 범위 내에서 자연스럽게 굴곡을 형성하여 단조로움을 탈피.
- 상단 초기 3개 역 배치 영역과의 최소 40px 이상 안전 간격을 확보하여 시작 즉시 강 교차 0개(무장애)를 항시 보장.

### 6.2.1 초기 3개 역 무결성 규칙
- 형태: 원형(Circle), 삼각형(Triangle), 사각형(Square) 각각 1개씩 고유 배정.
- 색상: 코발트 블루(`#1D5299`), 코랄 레드(`#D84315`), 포레스트 그린(`#2E7D32`) 1:1 무중복 배정.
- 무장애 보장: 3개 역 간의 직선 경로에 강(River)과 산(Mountain)이 전혀 없는 위치로만 배치하여, 시작 즉시 다리/터널 없이 개통 가능.

### 6.2.2 동적 맵 확장 및 지형 연장 (Weekly Map & Terrain Expansion, D-28)
- **주기**: 인게임 시간 1주일 (7일 = 168시간)마다 주기적 트리거.
- **수식**:
  $$\text{NewWidth} = \text{CurrentWidth} \times \left(1 + \frac{1}{6}\right)$$
  $$\text{NewHeight} = \text{CurrentHeight} \times \left(1 + \frac{1}{6}\right)$$
- **중심축 유지**: 플레이 구역의 중심점 $(C_x, C_y)$을 기준으로 상하좌우 대칭으로 확장.
- **물리 단위**: 그리드 1칸(`64px × 64px`) = `1m × 1m` (면적 수치는 화면에 표시하지 않음).
- **강 지형 연장**: 맵 너비 확장에 따라 기존 강(`river_0`)의 서쪽/동쪽 끝단을 새로운 맵 경계선(`mapLeft`, `mapRight`)까지 80px 간격으로 유기적 연속 연장.
- **산악 지형 추가**: 확장된 외곽 공간에 산악 지형 1~2개를 절차적으로 추가 배치(기존 역, 기존 산, 강 지형과의 충돌 방지).

### 6.2.3 역 스폰 2중 스케줄 (24h 확정 + 12h 25% 보너스)
- **기본 스폰**: 인게임 시간 매 24시간(`simulation_time % 86400 == 0`)마다 1개 역 100% 확정 생성.
- **보너스 스폰**: 인게임 시간 매 12시간(`simulation_time % 43200 == 0`)마다 난수 발생(`randf() < 0.25`), 성공 시 1개 역 추가 생성.
- **최대 수용 역 한도**: 최대 24개 역까지 자연스럽게 확장.

### 6.2.4 인프라 접근성 보장 및 데드락 방지 알고리즘 (D-16)
플레이어는 시작 시 다리 1개, 터널 1개만을 가지고 시작하므로, 다리 2개 또는 터널 2개가 필요한 역이 나타나면 플레이어가 영구적으로 연결할 수 없는 불합리한 상황이 발생한다.
- **검증 규칙**:
  임의의 신규 역 후보 좌표 $P_{\text{cand}}$에 대해, 이미 배치된 역들의 집합 $S = \{s_1, s_2, \dots, s_k\}$와의 직선 연결 세그먼트를 평가한다.
  - 각 $s_i \in S$에 대해 선분 $\overline{P_{\text{cand}} s_i}$가 교차하는 강의 수 $B(s_i)$와 산의 수 $T(s_i)$를 계산한다.
  - **유효성 판정 조건**:
    $$\exists s_i \in S \quad \text{s.t.} \quad B(s_i) \le 1 \quad \text{and} \quad T(s_i) \le 1$$
  - 즉, **기존 역 중 최소 1개 이상의 역과 다리 1개 이하 AND 터널 1개 이하로 연결 가능한 경우에만 유효한 위치로 승인**한다.
  - 만약 모든 기존 역과의 연결 경로가 다리 2개 이상을 요구하거나 터널 2개 이상을 요구하는 고립 구역이라면 즉시 후보를 폐기하고 재추첨한다.

### 6.2.5 혼잡도 3단계 경고 및 게임오버 판정
- `0 ~ 26명`: 정상 (`NORMAL`)
- `27명`: **1차 경고** (`WARN_1`) — 앰버(`#D97706`) 상단 경고 배너 + 토스트 + 경고음
- `28명`: **2차 경고** (`WARN_2`) — 딥 오렌지(`#EA580C`) 상단 경고 배너 + 토스트 + 경고음

# 7. 노선 및 열차 운행 인터랙션 사양

- **클릭-앤-팔로우 (Click-to-Connect)**:
  - 시작 역 클릭 시 4.5px 다이내믹 러버밴드 라인이 마우스 커서를 실시간 추적.
  - 목표 역 호버 시 32px 타겟 링과 글로우 스냅 + `"✔ 클릭하여 연결"` 힌트.
  - 목표 역 클릭 시 즉시 노선 연결 확정.
- **드래그-앤-드롭 (Drag-and-Drop)**: 시작 역에서 마우스를 누른 채 목표 역으로 드래그 후 릴리즈하여 연결.
- **지형 장애 실시간 피드백**: 강/산 통과 시 다리/터널이 부족하면 빨간색 라인 및 `"⚠ 다리 부족"` 피드백 표시.
- **순환선 지원**: 3개 이상 역을 가진 노선은 양 끝점을 연결하여 순환선 개통 가능.
- **안전 취소**: 빈 공간 클릭, 우클릭, `ESC` 키로 안전 취소.
